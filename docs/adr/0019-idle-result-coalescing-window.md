# 指挥官空闲时按安静窗口合并一批子代理结果

指挥官空闲时，每条子代理结果经前门唤起一个完整回合（ADR 0017）。真机上一批 8 个结果在约 20 秒内陆续返回，
指挥官被唤醒 6～8 次，每次都复述一遍，信息与 ↳ 行重复，还多付请求与 token。

改为：指挥官空闲时，结果先进发件箱等一个安静窗口——最后一条入队后 1.5 秒内没有新结果才唤醒，
从第一条入队起最多等 6 秒；指挥官在跑时不等，照旧立即经 steer 在句缝送达（正在跑的回合本身就是合并点）。
提示词同时要求不逐条复述结果。

这个等待是业务语义，不是拿计时替代事件：要回答的问题是“这一批还会不会马上再来一条”，宿主和子代理都没有
能回答它的事件，只能在时间上划界。送达本身仍按事件确认（ADR 0017），计时只决定什么时候发起这一次投递。

取值依据：同批并行的子代理往往在几秒内先后返回（dogfood 里相邻两条间隔约 2～3 秒），而一个唤醒回合本身要
数秒；1.5 秒能把紧挨着的结果并进同一次唤醒，回合开跑后再到的结果走句缝，不需要更长的窗口。6 秒上限保证
陆续不断地到达时也不会无限推迟。代价：指挥官空闲时单条结果最多晚 1.5 秒被看到（持续到达时最多 6 秒），
相对子代理动辄数分钟的运行时间可以忽略。

替代方案：只靠提示词要求不复述——唤醒次数不变，每次唤醒仍是一个完整请求。等同批 start 全部返回再投——
流水线里一个快的结果要等慢的兄弟，可能晚几十分钟。

## 后果

安静窗口只经 Master 的依赖注入（`wakeQuietMs`）可调（测试置 0 或很小的值），没有用户配置项；投递失败的重试计时与此无关。
