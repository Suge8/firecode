# 闲时前门投递以宿主记录这条消息为送达

会话歇透时，Master 事件与观察员发言经 `deliver.ts` 走前门 `sendUserMessage` 唤起回合（理由见根 AGENTS.md 硬约束）。
此前的实现假设它会等整个唤醒回合结束才返回，Master 在投递完成后扣在飞子代理数，以为扣减时指挥官回合已经在跑。
宿主（pi 1.0.2）扩展 API 的 `sendUserMessage` 实际返回 void、只把消息交给会话就走，唤醒回合稍后才 `agent_start`。
中间这个空档里在飞数先归零、指挥官回合还没开始，busy.ts 判定会话歇下：真机上一段 6 分钟的会话被记成 3 秒，Bark 提前推送。

改为按事实确认：闲时投递等下一个回合（`agent_start` 之后）的第一条消息。它正是这条信封（role=user、正文原样）才算送达；
是别的消息（宿主开回合前拒绝了这条——只走宿主 emitError，扩展订阅不到——随后用户自己发话开了回合），说明这条没进来，
会话此刻正忙，同一节拍改走 steer 补投、句缝送达。两种情况 resolve 时指挥官回合都已在跑，扣在飞数不会误报歇下；
补投保证事件不会因为“看到任何回合就算送达”而被 ack 后静默丢失。之后再没有任何回合时投递保持未完成，宁可不歇下，
也不误报歇下；纯事件驱动，没有计时器。`tests/delivery-contract.test.ts` 钉住两条宿主事实：扩展 `sendUserMessage` 立即返回、
不等回合；唤醒回合在 `agent_start` 后原样记录这条用户消息。宿主改变其一时对应用例会变红。

替代方案：见到下一次 `agent_start` 就算送达——宿主拒绝后用户自己开的回合会被误认，事件被 ack 却没进上下文；
加超时兜底——引入计时参数，且超时后仍无法判断事件是否进了上下文。busy.ts 另记“前门已发、未开始”——要求 busy 知道
投递细节，等于第二份投递状态；在 deliver 一处定义“送达”，Master 与观察员都不用改。

## 后果

Master 的在飞数与轮记录不再在唤醒前断开；观察员在唤醒回合开始前不评估新增量。投递失败时 Master 重试，
观察员只丢弃这一条建议并提示（建议过时后重投没有价值）。
