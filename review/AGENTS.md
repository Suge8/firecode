# review：`/fire-review` 对抗性审查

多模型并行审、顾问仲裁、checkpoint、结果卡、审查进度发布。零外部依赖。

## 状态与生命周期

状态机（相、判别联合、不变量）见 `state.ts` 头注释。修复回合与总结回合共用同一条 `turn` 生命周期（`pending → running → done`，总结回合结束直接落 settled）；总结类型与修复反馈都由 `history` 末轮推出，不另存。已收口轮的全文只存在 `reviewers[].details` 一处，其余文本经 `roundText` / `findingsOf` 推出。

分工见 `run.ts`、`index.ts` 头注释。命令入口的 START 一律先排队，开审只经 `advance` 在 idle 门里发生，没有“直接开审”的第二条路径；用户取消是 `notify_cancelled` 通知效果，不是卡。对外中止入口是命令 `/fire-review --cancel`（常量在 `outcome.ts`，Master 的 interrupt 用它）：与 esc 同一个 CANCEL 事件，顾问阶段也整场取消而不是只跳过咨询；没有进行中的审查时只提示，不留拒绝记录，配置坏掉时同样可用。

`Run.release()` 中止在途工作与投递、停看门狗、放占用、还界面、通知宿主不再持有；它幂等，释放后的 dispatch 一律忽略。

`registerReview(pi, options)` 的 `options`：`enabled`（用户关闭时只封存遗留的活动 checkpoint）、`configBroken`（features 配置坏掉不是关闭，保留 checkpoint）、`pool`（审查/顾问会话开在这个池里：进程里唯一的子会话池，由根 `index.ts` 传入，本模块不自建）、`runSession`（审查/顾问会话执行器，测试注入脚本化会话用，给了就不需要 `pool`；两者都没有时注册即报错）。会话级状态的隔离方式见 `index.ts` 头注释。

reload/new/resume/fork 保留可恢复状态，quit 才落终态；子会话被根级 `spawn.ts` 的池释放时同样先收到 quit 再 dispose。

`session_start` 只恢复 checkpoint，宿主在所有异步 session_start handler 完成后发出的 `resources_discover` 才允许推进；`agent_settled` 由 review 判断能否开审。`agent_start` 另作竞态兜底：若审查仍在跑，先 abort 并等待全部审查会话释放（dispose，bash 子进程随 abort 同步被杀），执行模型才进入 turn_start。审查者的中断不等 pi 的 `session.abort()` 返回：模型流卡在半开连接上时它永不返回（Bun fetch 在网络切换后不保证响应 AbortSignal，pi 的 agent loop 也没有 abort 竞争），等它会把 kill 与会话关闭一起拖死；卡死的审查者会话在进程里惰性留到 TCP 层放弃。

`awaiting_fix` 的 `turn` 写进 checkpoint；reload 会把未完成的反馈重置为 pending 重投，只有 done 才进入下一审查轮。反馈经根级 `deliver.ts` 投递（空闲时前门唤起，回合照常经过 `before_agent_start`；投递带 Run 的终止信号，收口后不再补投旧信封），以消息送达为回执、没有计时器：deliver resolve 推进 pending → running，最终 `agent_end` 确认未以 error/aborted 结束才 done，以 error/aborted 结束按用户取消收尾。宿主在回合开始前拒收前门消息时 deliver 不 resolve，状态停在 pending 并继续持有占用，用户下次发话后由那个回合把这条信封补投进去才解开（取舍与 Master 事件一致，已确认接受）；等待期间 `delivering` 标记挡住重复推进。

质量裁决终态（通过 / 顾问叫停 / maxRounds 用尽）先经 `summarizing` 相：结果卡照发，再投递带反循环禁令的总结提示（经 `deliver.ts` 投递，回执与收尾规则同修复反馈），总结回合结束才落 `settled`；总结生命周期持久化，reload 重投未确认总结，失败静默收尾不升级；事故终态（取消/超时/基础设施错误/quit）不烧总结回合。修复反馈、总结提示与状态卡 content 统一经 `deliver.ts` 的 `wrapEnvelope` 包在 `<firecode_review>` 中，折叠界面据此把它们归入过程（空闲时它们是前门送达的用户消息，显示为折叠的一行 ↳）；details 保持原始卡片数据。给审查者的证据（`sessionEntries`）过滤掉审查自己的信封：自定义消息与整条由审查信封构成的用户消息都不进证据。占用标签持有到总结完成，Master 的审查等待自然捕获总结作为最终回复。

`outcome.ts` 是外部读取审查进度与终态判定的唯一入口，checkpoint 格式仍归 review 所有：订阅方用 `outcomeOfEntry` / `reviewProgressOf` 从刚追加的记录增量解析，`readReviewOutcome` 只在需要整份文件时（回合结束兜底）用。终态读取按 `settled.end` 判定：通过 / 顾问叫停（带裁决）/ 轮数用尽 / 故障 / 取消（`cancelled`，不是故障也不是质量裁决）/ 总体超时；不从末轮结果猜（修复回合期间被取消，末轮仍是 failed，曾被读成“轮数用尽”）。故障的 `reason` 取该轮故障说明原文（超时、供应商报错都写在 `error` 里），取消与超时给人话，读取方不得把枚举名当原因展示。命令入口拒绝启动（配置问题、已有审查在跑、参数错误）统一经 `checkpoint.ts` 的 `recordRefusal` 写一条拒绝记录（不动 checkpoint，不碰进行中的审查），有 UI 时另行通知；无 UI 的 Worker 里这条记录是原因唯一的出口，`outcome.ts` 把它读成 `refused`（`runId` 是这次拒绝的 id，`message` 是原文），Master 原样报给指挥官。新增拒绝分支必须走同一个 `refuse`。

## 持久化

三种记录与快照内容见 `checkpoint.ts` 头注释。恢复时 `readCheckpoint` 按轮记录补回内存里的 `history`，没有存档与旧版本存档按没有处理、无提示；同版本存档损坏（字段无效，或快照记的轮数与轮记录条数对不上，不分审查是否已收口）作废并经 `onDamaged` 在 `session_start` 提示用户重新 `/fire-review`。Master 读结果的 `outcome.ts` 只读快照里的 `rounds` 与 `last`，不读轮记录。

写入口是 `CheckpointWriter`（记得已写过多少轮全文）；没有写入凭证或并发写者检测——同一会话文件只有一个活动运行时。存储格式变化直接升 `VERSION`，旧档按没有处理，不写迁移。持久化失败不能当成功继续：通知、尽力补写终态（否则重启会把磁盘上的活动 checkpoint 恢复成幽灵审查）、释放。

## 卡片与审查进度

结果卡使用 pi 原生背景卡与完整 Markdown：通过为绿底，未通过、终止与异常为红底，其余为紫底；标题前是单色字形，字形与语义色按卡种类在 `card.ts` 的 `MARKS` 一处定义（渲染时按种类取用；details 校验接受的卡种类也由它派生，`details.tone` 同时是折叠界面判断失败色的依据），不用 emoji 与品牌火焰；排队相不发卡，开始卡只发第 1 轮，后续轮边界由结果卡轮号承担。每轮 findings 只完整显示一次；达到顾问阈值时先显示失败卡，若顾问裁定 stop，终止卡只显示顾问裁决，不再复制同一份 findings。

卡一律以 `triggerTurn: false` 发送：不唤醒执行模型；宿主在回合进行中会把它推迟到本回合末追加，空闲时当场追加，所以超时等事故卡在执行模型忙时也照常发出，没有应用层的待发队列。

顾问卡与审查结果卡同构：裁决进标题（顾问指引 · 继续修复），正文首行为粗体模型分节，三段正文标题加粗且段间补空行（Markdown 把单换行折进同段，不补会糊成一块）。顾问会话没有产出（超时、供应商报错）不终止审查：跳过咨询，带着本轮发现继续修复，并发一张“顾问不可用，已跳过”的卡写明原因；用户按 esc 跳过咨询同一路径，不发卡。

`ReviewProgress` 只有审查相的票数可数；进度只读 reducer 的当前状态，不另派生逐审查者工具进度或摘要，也不为它设计时器。`ReviewUi` 每场审查一个实例，各自记着要还原的标题与编辑器；终端标题是“审查中 R轮次 · 会话名”。

`ui.ts` 等待模型时接管编辑器：只拦文字输入与提交（插话会污染本轮审查的会话证据），应用级按键（切模型、退出……）与扩展快捷键照常工作；esc/Ctrl+C 随时取消审查（顾问阶段 esc 跳过咨询），`awaiting_fix` 与 `summarizing` 相把输入交还用户。接管时保存 `getEditorComponent()` 的当前工厂，解锁还原它（可能是别的扩展设置的自定义编辑器，不是宿主默认）；锁定期间输入区收起成一行暗色“审查进行中 · esc 取消”（快捷键文案取自 keybindings），上下边框取自被包住的编辑器。按键必须经 keybindings/终端转义序列匹配，不能只比裸 `\x1b`。终端标题还原时手抄宿主默认标题格式（宿主没有公开接口，理由与源码位置见 `ui.ts` 的 `restoredTitle`，升级 pi 时核对 `APP_TITLE`）。无 TUI 的会话照常运行完整审查循环，不访问 UI；取消由会话退出或总体 watchdog 负责，结果卡仍写入会话记录。

审查会话的最终回复取会话事件中完整的 assistant 消息。

给审查者的会话证据有篇幅预算：单条消息超过 3000 字只给前 3000 字，命令轨迹超过 200 字截短，总结材料超过 4000 字截短；每个截断处都写明是证据截断、原文多少字，消息与命令轨迹的截断还给出会话文件路径，审查提示说明这些标记不是回复没写完、需要时读文件核对（裸“[…]”曾让审查者把完整的长交付物连判三轮未完成）。总预算超出时保留连续的最近后缀，省略标记写在缺口处。

## 文案与契约字段名

用户可见文案、拼给模型的提示正文与校验报错都在 `messages.ts`；审查/顾问的政策提示词在 `prompts/*.{zh,en}.md`。
`messages.ts` 的 `terms` 是审查输出契约与结果卡字段名（发现、严重程度、证据、卡点、原因、用时、模型……）的唯一来源：卡片与汇总取当前语言，
解析端（`reviewer.ts` 校验审查者输出、`state.ts` 回顾已收口问题、`tools/machine.ts` 取审查卡预览）经 `termPattern` / `fieldLine` 两种语言都认。
取舍：只认当前语言更省，但会话历史会跨语言（切换 `language` 后恢复旧会话，旧卡片与滚动开放清单里仍是原语言），模型也可能不照提示词语言写字段名，
只认当前语言会让整票作废为格式错误、旧卡片预览退化成第一句正文。代价是多一种语言的字段名要随契约同步，仅此一处。
发现字段名只认当前提示词的两种语言写法，不留旧措辞别名：契约改字时同步改 `terms` 与提示词，已落盘的旧措辞发现按格式无效处理。

字段行（`- **字段名**：值`，含 PASS 的证据行）的容忍度只有一份：`fieldLine` 容忍列表符、粗体包裹（含冒号写进粗体内）与冒号后的粗体开头；判定行的装饰剥离见 `verdict.ts` 头注释。严重程度只看行内开头的词（高/中能阻塞，「高（理由）」「**高**」都算），低严重度不得阻塞。

## 占用信号

审查占用频道的定义与读法见 `busy.ts` 头注释，review 是唯一发布者；终态、取消、退出时发布 `active:false`，reload 恢复时重新持有。订阅方故障由宿主事件总线隔离，不影响审查。

## 契约与配置

审查政策与 PASS/FAIL 输出契约以 `prompts/review.{zh,en}.md` 为唯一事实源，经 spawn 整体替换系统提示；需求、
关注点、往轮结果和完整会话记录留在 user prompt，记录中的需求照常生效，但不能反向改写审查职责、工具边界与
输出契约。审查会话使用 memory 持久化，关闭自动扩展、Skill、
模板和上下文注入；项目约定由审查者按 system policy 主动读取适用的 AGENTS.md。每条 FAIL 发现必须六要素齐全（标题、严重程度、问题、违反的约定与期望、证据、验证命令，标签
加粗；校验容忍非粗体）。**格式无效但以 FAIL 开头的票仍按未通过计**：它是审查者提出的阻断意见，当缺席会让另一票的 PASS 翻盘；原文随修复反馈与结果卡交出，违例说明（点名真实原因，如“严重程度写的是低”）作为前注。首行不是判定词、格式无效的 PASS 才作废为缺席票。有裁决就成轮：一轮里只要有一票 PASS/FAIL，就按有裁决的票形成结论，缺席者（会话故障、超时、输出契约违例）在结论里点名而不阻断；全员缺席才是基础设施不可用。往轮发现清单随轮注入顾问裁决
（`prompt.ts`），审查者不得原样重提已仲裁事项——僵尸发现收敛闭环。

审查者的只读是契约而非能力边界：`review.tools` 里不得含 write/edit（配置解析直接拒绝，`session.ts` 不再二次过滤），保留的 `bash` 仍能在项目目录执行任意
命令。保留 bash 是有意的——审查者要跑测试取证；真需要物理隔离得上容器或只读挂载。

config.jsonc 的 `review` 节必须显式完整配置（字段见 `config.ts`）；公开包不内置依赖个人认证或偏好的模型。
该节有任何配置问题时，`/fire-review` 与 checkpoint 恢复都拒绝启动；活动 checkpoint 保持原样，修好配置并重启后继续恢复。
