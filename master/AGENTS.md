# master：进程内多 Agent 指挥官

新会话按 `master.autoActivate` 注入七命令工具 `subagents` 与池快照查询 `subagents_list`；默认开启。裸 `/fire-master` 翻转当前会话（关闭时若有子代理在跑，有界面先 `ctx.ui.confirm` 确认；无界面照旧直接关），`/fire-master status` 查看状态；下一次会话仍按配置决定，命令不写回。配置或角色表有误时拒绝激活，不用默认模型代替。角色可用性每次会话开始核对一次（`roles.ts`），交给那一次的运行时：解析不出模型的角色告警一次、不进提示词（系统提示是缓存前缀，会话内不变）。派发只认配置里的角色名，不拿这份核对或任何缓存的可用模型挡：凭据会在会话中途增减，模型解析与凭据核对只在开会话后第一次请求时由路由做，解析不出按失败事件告知（“模型链已用尽”）。

## 运行时

各文件的职责见头注释（`ls master/`），头注释之外：运行时旋钮（空闲释放、续跑提醒时限、合并唤醒窗口、事件重试间隔、卡住时限、瞬时失败的冷却阶梯）的默认值与说明只在根 `timing.ts`，经池的 `pool.timing` 读取；`runtime.ts` 的 `commit` 是 await 后唯一的重读与写回点，`settle` 是回到 idle（落定、被中断、暂停、续跑失败）的唯一执行口（固定顺序：写档、登记空闲、入队事件），`schedulePublish` 是在飞数与名册的唯一发布点；档案标记怎么随转移清掉只写在 `state.ts` 的 `transition`；信封词汇见根 AGENTS「文案」。

Worker 是主进程内的 SDK 子会话而非独立进程：reload 会中断在飞回合（JSONL 与审查义务保留、可续派），换来父进程退出即全停、无幽灵进程与跨进程对账。池只管 Worker 生命周期与结果回传，不建 Goal、Task、任务板或消息总线；多个 Worker 可并行写同一 checkout，没有写租约，集成与验证归指挥官。

所有子会话只经根级 `spawn.ts` 创建（进程里只有一个池：根 `index.ts` 建一次，Master 与 Review——含 Worker 会话里的审查——共用，模型运行时只读一次；各自的会话互不牵连）：它封装 Pi SDK 会话、模型、工具、扩展、
系统提示、上下文文件与持久化。池由入口建并传给各方，注册进子会话的是主会话已加载的这份 FireCode（子会话模式：只有守卫、轮记录等与界面无关的部分）；宿主为子会话从磁盘另读的 FireCode 在加载标记下不注册。否则 FireCode 在会话中途更新后，新开的 Worker 会跑新代码而指挥官仍是旧代码，审查 checkpoint 等落盘约定对不上；改完 FireCode 要 reload 指挥官，Worker 才用上新代码。审查会话隔离，不带任何扩展；Master 关闭只释放落盘的子代理会话（`disposeWorkers`），审查的内存会话归创建它们的一方，不会被掐断。模型链由 `model-route.ts` 在共享池内解析和路由，冷却表跨池进程共享；配置链以外的模型不被选择。模型原子只在池里解析：每个池只建一份 ModelRuntime（auth.json 与 models.json 只读一次），扩展注册的 provider 在模型解析时不可见。这份 ModelRuntime 同时交给池里建出的每个子会话，所以某个子会话里扩展注册的 provider 对同池其他子会话也可见（宿主跨会话复用服务也是如此）。单写者登记挂在 globalThis 上，宿主重新求值模块图时仍是进程唯一。Worker 使用 file 会话，文件位于主会话目录下的 `subagents/`，不会出现在 `/resume`；会话路径是档案身份的唯一事实源。同一路径只允许一个热会话持有者。子会话按目标 cwd 起项目信任（`spawn.ts` 的 `projectTrusted`，与宿主非交互路径同一判定：无需信任的项目资源就信任，否则取宿主信任存储里最近的显式决定，没有决定时看全局 `defaultProjectTrust` 是否为 always；子会话无法弹窗，ask 与只对主会话本次生效的选择都按不信任），资源加载器与会话共用同一个 SettingsManager，它的压缩设置（`compaction.modelOverrides` 等）按会话此刻路由到的物理模型解析（`model-route.ts` 的 `followRoute`）。

Worker 档案是 v10：`working / idle / reviewing` 三态，以 `role` 记录派发角色、`model` 与 `thinking` 记录实际原子（只由路由回调写，第一次请求选定模型时才有：start 之后、选定之前两者都没有，列表与名册省略模型；原子属于角色与思考档覆盖，send 换了其中任何一个就在写入新角色的同一处清掉（`transition.reassigned`），路由重配后忘掉上一次选定、下一次选定一定写回，选不出就一直没有），可选的 `thinkingOverride` 记录指挥官在 start/send 指定的思考档（开会话与重配路由只从它取，冷热一致；send 每次按自己的 thinking 改写），`cwd` 记录工作目录（start 必写，没有它的档案按格式损坏拒读），`launch` 记录启动序；另有 `interruptedAt`、`reviewNeeded`、`reloadInterrupted` 与 `resume` 四个独立标记（`reloadInterrupted`、`resume`、`thinkingOverride`、`origin` 与 `viewPrompts` 是可选字段，旧档没有它们照常读，版本不变）。idle 带 `resume`（时刻、原因、是否续审）就是瞬时故障后的暂停，见下「暂停与自动续跑」。旧版档案由 `MasterStore` 丢弃并告知，不迁移；比当前更新的版本（降级）明确失败，不删档案。`MasterStore` 是档案唯一所有者：每次变更先原子写盘、成功才换内存，写盘失败照常报错且内存与磁盘不分叉（kill 报错就是没删）；落定、计时器这类没有调用方的续延写盘失败时经 `MasterRuntime.detached` 报给用户，档案停在写前，reload 时照常收敛。列表始终按启动序（`launch`）排列，读者不再二次排序；载入时（`transition.converged`）把在飞状态收敛为 `idle + interruptedAt + reloadInterrupted`（保留会话与审查义务），激活时只对带 `reloadInterrupted` 的票补挂续跑提醒（按 `interruptedAt` 补算剩余时限，提醒发出前再 reload 也不丢）——指挥官自己 interrupt 的不带它，提醒的 pending 落盘、`send`/`review` 接手或 `ack` 时清掉（pending 落盘失败就保留，reload 后再提醒）。池变空（删最后一票、载入空池）就删档案文件。首次续派会前置现场核对提示。

热冷只属于运行时缓存：池不按会话事件自判释放，只有 Master 在回合落定、中断落定、审查落定时（`settle`）才经池的 `markIdle` 起释放计时，因此 reviewing 中的 Worker（审查期间它自己是闲的，修复回合结束也会落定）不会被释放；释放热会话后池通知持有方，Master 随即退订，不再持有已关闭的会话；释放（到期、kill、换目录重开、Master 停用）先中止在跑的回合并等它落定（最多 `timing.ts` 的 `abortSettleMs`，卡死的流不拖住释放），再经该会话的 extensionRunner 发 `session_shutdown`（reason quit）让会话内扩展收口，最后 dispose——与宿主替换会话的顺序一致：少了第一步，被中止那一轮的 `agent_settled` 会晚于 `session_shutdown` 到达；少了第二步，会话里跑着的 fire-review 会成为握着死 ctx 的孤儿。档案与 JSONL 保留；后续 `send` 打开原会话继续，释放的 session_shutdown 还在收口时，同一路径的重开（send、自动续跑）等它落定再开，不报“已持有”。池的 `getSession` 是纯查询（视图、steer、interrupt 只看不占）；要在会话上开回合的 `send`/`review`/自动续跑经 `hold` 取消释放计时，开回合前经池的 `idle` 等宿主真正空闲（宿主的 `waitForIdle` 在 agent_settled 处理器还在跑时就返回，那时开的回合被宿主推迟、调用当场返回，回合无人跟踪；判据见 `spawn.ts`）；这些都在动作返回之后的后台跑（见下「动作不阻塞」），释放计时由这次运行的落定补回。同一路径还在建的会话（例如指挥官会话关闭后才建好、马上被释放的那个）也要等它有了去向。票身份只在池里核对（spawn 的 `claim`，Master 传 `runtime.owned`）：同一路径的 spawn 都在等完打开与释放之后汇合，所以在那里、真正新建之前问一次（被 kill 或会话已关就不建，“已在等释放时被 kill”也挡得住），建好交出前再问一次（不要就当场释放，下一次 spawn 等到的就是最终去向）。热会话在开回合前被 kill 时由 kill 自己释放，回合入口见票已换就不开回合。档案存在但会话文件不存在时（子代理在第一条回复落盘之前就被中断或释放，宿主此前没写文件）没有上下文可恢复，`send`/`review` 在同一路径上新开会话继续，`tail` 与全过程视图读到空记录。`kill` 在同步段内删档案与该名下的整条运行时事实（计时器、订阅、当前工具、落定结局一次清掉）就返回，热会话在后台先发 session_shutdown 收口再释放（不等：处理器没有时限，被 kill 的路径也不会再开），永不删除 JSONL。异步回写只属于未关闭的当前 runtime；会话关闭先清空当前 runtime 并置 closed，再释放池、订阅与定时器，迟到任务不写状态、投递、UI 或持久化（`MasterRuntime.find` 在 closed 后返回 undefined，落定回调据此直接放弃）。

档案存在 Pi Agent 目录（`getAgentDir()`，含 `PI_CODING_AGENT_DIR` 覆写）的 `tmp/firecode-master-<主会话 id>.json`，事件的 pending/ack 存在主会话 JSONL：fork 出的会话带着 pending 却没有档案，重投时可能提到不在池里的 Worker——这是已知边缘，接受。

## 工具契约

`subagents` 只有七个命令动作，结构上都要求 Worker。role 枚举列全部配置角色；系统提示只列会话开始时有可用候选的角色，派发其他配置角色照常起跑，解析不出模型时以失败事件告知；不在配置里的角色名（档案还是改配置前的角色）报错并列出可用角色。

- `start`：显式指定角色表内的 role 和短名；可用 thinking 覆盖角色原子档，可带 cwd、review。开不成（模型解析不出、会话打不开）与回合失败一样落定为“失败”：票以 idle 留在池里（档案与会话路径保留），指挥官 send 重试（可带 role/cwd 换掉出错的那项）或 kill，不会被自动撤掉，同名再 start 报“已存在”。
- `send`：working Worker 的普通 send 是补话：记下就返回 `{ queued: true }`，回合在飞后经宿主 `session.steer` 在句缝送达，不打断（仅回合确在流式时；steer 是子会话自己的消息队列，与根 AGENTS.md「硬约束」里主会话的唤醒问题无关，且只在流式中使用，不会唤起歇透会话）；回合没开成、已记下中断意图或送进时已结束的补话作为“补充说明未送达”事件回报（`run.ts` 的 `steerTurn`）。已记下中断意图的票拒绝补话，提示等“被中断”事件。切换 role、thinking 或 cwd 要求 Worker 空闲，working 时提示先 `interrupt`，reviewing 时等落定。省略 role 时沿用，显式传入时原地切换角色；thinking 可单独覆盖。带 cwd 时释放热会话并以新目录重开同一份 JSONL（不新建会话），档案记新 cwd；Worker 的 cwd 已不存在且未带 cwd 时明确报错并提示带 cwd。steer 入队后回合若以中断等方式结束，滞留队列的补充说明在落定时清出并作为同一条事件回报指挥官重发，不留到下次 prompt。
- `interrupt`：记下意图就返回 `{ interrupting: true }`，不等回合；中止在回合真正在飞后做（`run.ts` 的 `interruptTurn`），结局经“被中断”事件告知，换说明的 send 等这条事件再发。暂停中的票当场按被中断落定、不发事件，返回 `{ interrupted: true }`。保留会话与义务；指挥官自己发起，所以不补发续跑提醒（只有会话重载打断的回合才提醒）。对 reviewing 的子代理：先在它的会话里执行 `review/outcome.ts` 的 `CANCEL_REVIEW_COMMAND`（与 esc 取消同一路径，审查以取消收场、终态 checkpoint 照写），再中止会话里可能在跑的修复/总结回合；审查监视看到取消的终态后按中断落定——回到 idle、带中断标记、审查义务保留（未履行，仍可再 review），指挥官收到“审查被中断”事件（不是失败）。取消没来得及生效、审查先以别的结局收场时（含已到总结相：取消只跳过总结、保留质量裁决），按那个结局落定。宿主 prompt 的前置阶段（input 处理器、鉴权）仍报空闲，落在那里的 abort 会被静默丢弃，处理器卡住时也没有时限，所以档案进入 working 的同一同步段就挂上回合（`runtime.ts` 的 `Turn`），碰会话的中止与补话都在后台等它真正在飞，动作本身不等：start 还在开会话、send 还在前置阶段时到达的 interrupt 只记意图，回合在飞后才中止，还没开回合就不调模型、直接按中断落定；中止失败就撤回意图、报给用户，回合按自己的结局落定。
- `review`：只对 idle Worker 显式发起 fire-review；写档进 reviewing 就返回 `{ reviewing: true }`，开会话与起审在后台，开不成按“审查未完成”落定，开好前到达的 interrupt 不起审、按“审查被中断”落定。
- `tail`：最后一条用户消息（指挥官派的活或视图补话；插件的事件与续跑提示是自定义消息，不算外部输入）之后的轨迹快照，不改变状态；格式与预算见 `trace.ts` 头注释。冷子代理的会话文件只经 `trace.ts` 的 `readWorkerSession` 读（全过程视图同用），只读载入、不改文件（不用宿主 `SessionManager.open`，它会给空文件写头、把旧版格式迁移后重写），文件不存在的规则也在那里。
- `ack`：清掉失败与被中断的活动列表行并取消未发出的续跑提醒与还没到点的自动续跑；只对 idle 生效，working/reviewing（含已到点的自动续跑）拒绝并提示改用 interrupt；审查义务未履行时拒绝。
- `kill`：移除池引用，返回 `{ killed: true }`；实现票完成收口或放弃整票时使用。

**动作不阻塞**：七个动作的返回路径上没有等宿主或扩展回调的 await。开会话（扩展加载、session_start）、宿主 prompt 的前置阶段（input 处理器、鉴权）、等子会话真正空闲（agent_settled 处理器）、释放会话（session_shutdown）、刷新可用模型（供应商鉴权）都没有时限，所以：`start` 校验后写档进 working 就返回 `{ started: true, worker }`，空闲票的 `send` 写档进 working 就返回 `{ sent: true }`（在跑票的补话返回 `{ queued: true }`），`review` 见上；开会话与开回合都在后台（`run.ts` 的 `runWorker`、`startReview`），开不成（会话打不开、鉴权或路由失败、扩展加载出错）按失败落定、经事件告知。同步段里只做必然结束的事：参数校验、角色名在配置里、本地文件系统的同步调用（cwd 的 `realpathSync`/`existsSync`、预分配会话路径、写档案）。暂停后的自动续跑是同一个形状：到点时同步写档进 working/reviewing，开会话在后台。

七个动作各是一个带类型的命令（`actions.ts`），只经 `commands` 调用：入口统一拒绝已关闭的运行时（全过程视图在指挥官关掉或 reload 后可能还握着旧运行时，报“会话已替换”）。工具处理表只把参数解析成命令输入；调用方身份（指挥官的工具 / 全过程视图）是 `send` 命令的独立参数 `origin`，工具一律以指挥官身份调用，全过程视图直接调 `commands.send`/`commands.interrupt`，所以模型无法冒充视图来源。

`subagents_list` 是零参数查询：模型结果只返回池快照（档案事实）；界面的展开行与 `/fire-master status` 由 `list-view.ts` 从相位投影，与活动列表同一说法。

同时 working/reviewing 的 Worker 最多 15 个：满额时 `start`、对空闲票的 `send` 与 `review` 直接拒绝并回报在飞清单，不排队；给在跑票的 steer 不受限，暂停后的自动续跑是已放行运行的接续，也不拦（可能短暂越过）。名字与 sessionPath 都必须唯一。校验与写档在同一同步段，同一 Worker 上的并发动作不另设单飞：后到的 send 看到的已是 working，作为补话交给这次回合。kill 赢过迟到的异步写回：await 之后的写回一律经 `commit` 重读最新档案再函数式更新；开会话期间被 kill 的运行不调模型、不留热会话与订阅、不复活档案。补话越过 input 处理器后回合已落定时清掉滞留队列并作为“未送达”事件回报，由指挥官重发；票已被 kill 就不回报。

## 活动列表

指挥官模式下，输入框上方逐行列出子代理：需要处理的置顶——红 `✗` 失败（含审查停止、审查未完成）与黄 `‖ 被中断`
留到指挥官 ack 或 kill，黄 `◌` 加动作后的 `· N 分钟无输出` 表示在跑的子代理到了卡住时限（`Timing.stallMs`，默认 30 分钟）仍没有任何输出、有输出立即恢复；然后是在跑、审查中与暂停（灰 `‥` 加“暂停至 HH:MM”，读档案，reload 后照样显示）的行，
再是 `✓ N 个已完成`（kill 后才去掉）与 `N 个空闲`（resume 后池里还在的、已 ack 的）。在跑的行最多显示 `max(4, 终端高度/6)` 行，超出折成 `+N 个在跑`；
三种折叠行的计数带一层浅灰底色表示可点，后面灰色列出被折叠的名字（放不下就少列）。点 `+N 个在跑` 展开全部、点“收起”折回，点 `✓ N 个已完成` 列出名字、结果首句与本次运行耗时，点 `N 个空闲` 列出空闲的子代理，再点收起；展开在你下一次发消息时自动收起。

排序、折叠与行布局见 `activity-list.ts`、`activity.ts` 头注释。相位（分组、在做什么与时刻）只在 `phase.ts` 判定：活动列表、全过程视图上横线、`subagents_list`、`/fire-master status`、名册与停摆唤醒都读它，状态词只有 `messages.ts` 的 `phase` 一张表。底栏只发布纯文字“指挥官”；相位的输入由 runtime 从档案加 live 表投影一次给出（`activityFacts`），落定事实（时刻、成败与说明）只在 live 里一份，reload 后哪里都不展示历史（池查询也不退回会话文件时间）；列表冻结的耗时与 `subagents_list` 的“落定 X 前”共用这一份。活动列表与全过程视图由 `index.ts` 挂到 runtime 上，runtime 不认识界面，只经 `onChange` 通知重绘。master/ 内无依赖环、状态与调度文件不 import 界面文件（含只有类型的导入），由 `scripts/deps.ts` 随 `bun run typecheck` 检查，界面文件名单也在那里。`ctrl+o` 不展开活动列表的原因：它常驻输入框上方，再展开只会挤掉正文视口。

## 进展行

在跑（working）的子代理可以有一句“现在在做什么”，显示在活动列表的在跑行（替代工具动作，卡住行不替代；名册的“在做什么”同一条规则）与全过程视图头部；模型链取顶层 `background.model`（与压缩摘要共用，见根 AGENTS 的 `background/`），省略 `background` 即关闭（每次生成都是真实调用，不替用户选模型）。触发、输入边界与失败口径见 `progress.ts` 头注释，延迟与冷却走根级 `completeOnChain`（与 Worker 共用冷却表，输出被截断不冷却）。它只给人看：不进指挥官上下文，不发事件；停摆事件只在卡住时发，读到的总是工具动作。以 stop 收尾的最终回复不触发生成（回合马上落定）。间隔在 `timing.ts`（首句 30 秒、之后至少 2 分钟）。实测（gpt-6-luna/low 与 claude-haiku-5-5/low 各 10 次，约 1.6k 字符输入）：luna p50 2.2s、每次约 $0.00009，haiku p50 3.0s、约 $0.00007，模板把 haiku 放在前面：同一条链也写压缩摘要，真实会话重放里 haiku 摘要保住后续要用的细节 46%、luna 33%；进展行因此慢约 0.8 秒，只给人看，可忽略。

## 暂停与自动续跑

瞬时故障（网络、过载、限流、写明重置时刻的额度窗口；分类与冷却在根级 `model-route.ts`）的处置分三层，各层只认自己的事实：

- 宿主：同一模型上的短重试（`settings.retry`，默认 3 次、2/4/8 秒）。
- 路由：短重试用完后冷却该模型、同一回合换链上的下一个；整条链都在冷却时抛“链已用尽”结束回合。冷却到期取报错里的重置时刻，读不出就按 `Timing.cooldownMs` 阶梯。宿主再重试这条路由报错时重新选模型，不把刚冷却的模型交出去（否则报错文本命中宿主可重试模式时会在同一回合里无限循环）。`routePause` 回答“这条链此刻是否整条暂停、何时恢复”：最近一个任务里实际失败的模型全是瞬时失败、每个候选都有冷却记录、且至少一个是瞬时失败；这次有模型以非瞬时错误失败就不暂停，别的候选的瞬时冷却盖不住要人处理的错误。
- Master：回合以 error 收场且 `routePause` 有值时不报失败，档案记 `idle + resume`，这次运行第一次暂停时投一条“已暂停”说明（只告知不唤醒，写明到何时、为何），按 `resume.at` 挂计时，到时在原会话以续跑提示（自定义消息）开回合；续跑又失败就再暂停、不再告知（“已告知过”只读档案：暂停前已带 `resume` 就是同一次运行里的再次暂停，跨 reload 也只告知一次）。审查以 `retry` 收场（见 review/AGENTS.md）同样暂停，到时重新发起 fire-review，审查义务不变。本次运行的起点与来源沿用暂停前的，落定事件只有续跑结束那一条。计时只在进程内，事实在档案：激活时对每个带 `resume` 的票重挂，所以等待中 reload 只续一次；`resume.at` 可远超 setTimeout 上限（约 24.8 天，超了运行时会立即触发），计时截到上限、提前醒来就按同一时刻重挂（根 `timing.ts` 的 `delayUntil`，指挥官回合的补唤醒同一处理）。自动续跑开始后 `resume` 留到这次运行落定才清：续跑中被 reload 打断时载入收敛回暂停（不带 `reloadInterrupted`、不发续跑提醒）并立即再续。send、review、interrupt（按被中断落定）、ack 与 kill 都作废还没到点的续跑。到点时续跑在同一同步段把档案写回 working/reviewing（开会话在后台），从此它就是在跑的运行：要停用 interrupt，ack 按非 idle 拒绝并提示改用 interrupt；不另设“取消意图”。续跑开不成（会话打不开、角色已删）按失败交给指挥官。非瞬时失败照常落定为失败。

指挥官自己的回合：宿主重试用完、最后一条回复是瞬时错误，而上一次完整收尾（stop 或用户中止）之后收到过子代理事件时，这些事件已确认送达不会再投，发件箱按同一阶梯补一次唤醒（“指挥官 续跑”），那一回合又失败就再挂；判定只读主会话分支、不另存，激活时重判一次。

## 投递与义务

落定事件的 pending/ack 与合并投递见 `outbox.ts` 头注释，合并窗口见 `index.ts`（安静窗口）与 `outbox.ts`（最长等待）。事件正文末尾的“本次运行”耗时与是否只告知由运行时算好再交发件箱（`runtime.ts` 的 `enqueue`、`event-format.ts`），发件箱不读档案与子代理会话；“当前任务 X”是给指挥官的时间信号（据已用时间安排并行），只追加在事件正文内，不触碰投递路径。

投递失败时事件回到队首，按 `Timing.eventRetryMs`（默认 5 秒）起逐次翻倍、封顶 60 秒的退避重试，一串连续失败只提示一次，直到送达；重试期间对应子代理仍算在飞。子代理会话里的扩展出错（事件处理器抛错）经 `spawn.ts` 的 `onExtensionError` 接线，作为“扩展出错”事件告知指挥官，同一处错误每个子代理只报一次。在跑的回合到卡住时限仍无输出时投“无输出”事件并唤醒指挥官，附正在跑的命令与本次运行已用时长；静默从本回合开始算，暂停后的自动续跑不把暂停期算进去；同一段静默只报一次，有输出后可再报。“已切换模型”与“已暂停”只告知不唤醒：同一会话会自动续跑，指挥官无事可做。

**视图起的运行**：档案里每次运行带一个来源（`origin`，省略即指挥官；类型 `RunOrigin`）与视图原话（`viewPrompts`），不另起状态机；它们随运行持久化，暂停后的自动续跑跨 reload 落定时照样只告知、带原话，运行落定、被中断、ack 或指挥官接手时清掉（`state.ts` 的 `transition`）。用户在全过程视图里给空闲子代理补话起的运行来源为 view：指挥官没在等它，所以不计入在飞数——主会话不因它进入进行中、不产生主会话轮记录；落定事件仍交给指挥官（它必须知道子代理状态变了），但经 `deliver.ts` 的 `inform` 只告知不唤醒（pending 里带 `inform`，reload 重投同样不唤醒；与唤醒事件同批时随那一批唤醒送达）。指挥官在这次运行进行中又 send 给同一子代理时来源转为 master，它从此在等；视图补进指挥官起的运行只记原话、不改来源。审查义务与失败行规则不变。

事件正文只在 `event-format.ts` 产文（标题、分节、失败口径、耗时行格式）；展示卡没有独立数据，`tools/machine.ts` 从信封正文解析标题、错误分节与“耗时：本次运行”行（中文界面的字样；英文界面是 `Error:`、`Elapsed: This run`）。标题里“名字是第一个空格前的词”这条两种语言都成立，改格式两侧同步，`tests/machine.test.ts` 与 `tests/i18n-master.test.ts` 用真实产文守这条链路。给模型的指令（续派或收口、审查义务）只放在标题之后的正文；被中断的正文只在有审查义务时提审查义务；待续跑只发给会话重载打断的回合，并说明是重载打断。

`review:true` 是持久化到票上的审查义务，不自动开审；它在 `send`、reload、中断和失败后保留并阻止 `ack`，由审查通过或质量裁决停止消除。`kill` 随整票删除义务。不在落定时自动开审：模型停下可能是在提问或交半成品，落定不等于完成；义务不灭归代码，送审时机归指挥官。

Master 调度行为与 Worker 行为的唯一事实源分别是 `prompts/master.<语言>.md` 与 `prompts/worker.<语言>.md`（zh/en 等价，改一边必须同步另一边）；修改委派纪律或 Worker 约束时改对应提示词，不在本文复述。提示词里引用事件产文的字样（子代理视图来源标记）必须与 `messages.ts` 里的一致，`tests/i18n-master.test.ts` 守这条。提示词不点具体角色名：角色名完全由配置决定，提示词按角色表里的适用场景指代（如“适用场景写着 CI、部署、长测试等待的角色”）。

## 隔离与配置

Worker 默认加载全部扩展，可由 `workerExcludeExtensions` 按完整路径或 basename 排除；用默认四工具，指挥官开着 codemode 时另加 codemode（同进程共用名额的加开见 `spawn.ts`）。Master 模块在 Worker 会话中只注册 edit/write checkout 守卫，不注册命令、subagents 或生命周期。守卫放行当前 checkout 与系统临时目录（交付物写在临时目录是正当用途）；bash 仍是可信能力（开放它是为了让 Worker 自跑测试；守卫只防误伤，物理隔离要容器或只读挂载，不在本插件范围），最终边界由委派纪律、自测、审查和指挥官验收共同承担。

Master 只跨模块读取 `review/outcome.ts`：审查进度与终态都由它从 Worker 会话里刚追加的记录增量解析，回合结束时才读一次文件兜底，Master 不解析 checkpoint 内部字段；工具行复用共享纯渲染组件。状态变化经 store 的 onChange 驱动状态栏，UI 只投影事实，不在动作调用点补绘。

## 全过程视图

点活动列表里任一子代理行打开它的全过程视图，行为与结构见 `worker-view.ts` 头注释。输入框上横线左边是状态与耗时（与活动列表同一说法），右边是名字与角色；下横线左边是第几个（n/N），右边是模型与按键提示，窄屏先省角色、模型和次要提示。Tab / Shift+Tab 按启动顺序换子代理，PageUp/PageDown 与滚轮翻看，拖动选中文字即复制，esc 返回。子代理被移除时上横线写“已移除”，不能再补话；之后对它的 send 报“子代理不存在：<名字>”。n/N 取档案的启动序（`activityFacts`），不随状态分组跳。

- 输入区与上下横线共用 `statusbar/render.ts` 的 `fitBorder`；调用点是活动列表的 `rowState`（上横线）与 `roundFromEntry`（轮记录），不在视图另算。
- 已发出未送达的补话读子会话的排队队列。
